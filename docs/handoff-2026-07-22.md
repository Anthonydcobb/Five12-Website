### The timezone bug (worth understanding — it masked a second issue)

Symptom: a Hog console that was off the network still showed a green ONLINE dot;
the device pane read `LAST SEEN -12910s ago` (negative). Root cause was
serialization, not discovery: the datetime columns are filled by
`datetime.utcnow()` (naive UTC), and `to_dict()` emitted a bare `.isoformat()`
with no `Z`/offset. Per the ECMAScript spec, an offset-less date-time string is
parsed as LOCAL time, so the browser placed every timestamp 4h in the future
(UTC-4), made elapsed time negative, and `negative < 90_000` is always true —
nothing could ever be offline. Fixed at the source with `_utc_iso()` in
`models.py` (emits trailing `Z`), plus a `parseUtc()` guard in
`NetworkMonitor.jsx`. This had also silently disabled the day's new "remove
offline" button, whose count uses the same predicate.

### Bolero battery panel — how it works

The Devices-page Bolero panel (`app/src/pages/Devices.jsx` `BoleroPanel`) now
shows the real antennas and the beltpacks attached to each with live battery
life. Backend is `backend/app/integrations/bolero.py`, read-only, polling.

Verified Riedel Bolero REST API (mapped from a real unit at `192.168.1.11`):

- Base `http://192.168.1.11/rest/…`, plain HTTP. Auth: HTTP Basic with the
  factory READ-ONLY account the GUI itself uses (`user` / `userPass`), override
  via `FIVE12_BOLERO_USER` / `FIVE12_BOLERO_PASS`. No login flow.
- `GET /rest/nodeStatus` — antennas + **live per-pack battery**. Each node's
  `bp[]` are the packs currently attached to that antenna; each carries
  `battery{status(=charge %), currentCharge(mAh), usbPower, batteryTemperature,
  batteryHealth, maxCharge}`, `signalLevel`, `timeslots{free,usable,interfered,
  warning}`, and the node has `ptpStatus{lockState}` (synced when `==2`).
- `GET /rest/nodeConfig` — `nodeId → name` (MBS LM 2 = .11, MBS LM 1 = .12).
- `GET /rest/bp` — DECT `id → bpConfig.bpName` (crew names). ~98 KB, so it is
  cached 300 s; the small live status polls every cycle.
- `ws://192.168.1.11/wsapp` exists for live push — out of scope (we poll).

Panel columns: Pack · Battery (live charge) · Health % (battery state-of-health,
NOT signal) · Antenna · Temp · State (⚡ when charging). Sorted lowest-battery
first. The simulator stays as the `?sim=1` fallback.

## Environment — read before touching the backend

Full list is in `docs/network-state.md` "Environment". The essentials:

1. Python is `backend/.venv/Scripts/python.exe` (has scapy, puresnmp, pytest,
   requests). A bare `python` off PATH does not.
2. Do NOT diagnose the interpreter from the process list — the venv is a
   redirector, so every venv-launched process reports the BASE python path.
   Test behaviour instead (does SNMP/Bolero return real data?).
3. Dev = MySQL (`five12_website`); desktop app = SQLite (`~/Five12Data/five12.db`).
   Apply any migration to BOTH (`flask db upgrade`, then again with
   `FLASK_CONFIG=desktop`).
4. Migrations live in `backend/migrations/` (the root `migrations/` is dead).
   Head is `b3f21c9d47ae`.
5. **The app spawns its own backend** — a model change without its migration
   breaks it on restart. Write the migration in the same change as the model.
6. After any backend change: `Get-Process python | Stop-Process -Force`. Nothing
   respawns them; a survivor reverts data silently.

Start the backend:

```powershell
cd backend
$env:FLASK_APP='app.py'
& .venv\Scripts\python.exe -m flask run --host=127.0.0.1 --port=5000 --no-reload
```

Frontend: `npm run dev` in `app/` (Vite on :5173, proxies `/api` to :5000).
